# Security Policy

## Supported Versions

| Version | Supported |
|---------|-----------|
| latest  | Best effort |
| < latest | Not maintained |

## Reporting a Vulnerability

If you discover a security vulnerability in Factur-X Engine, please report it responsibly.

**Do NOT open a public GitHub issue for security vulnerabilities.**

### How to Report

1. **Email**: Send details to **security@nexaflow.io**
2. **Include**: Affected version, reproduction steps, potential impact
3. Do not include production invoice data, credentials, license keys, or personal data.

### What to Expect

- Reports are reviewed on a best-effort basis; no acknowledgement, assessment,
  remediation, disclosure, or release time is guaranteed.
- We may credit reporters in release notes unless anonymity is requested.
- We do not intend to take legal action against good-faith researchers who avoid
  privacy violations, service disruption, and data destruction.

## Security Practices

- **Local processing**: Normal invoice-processing requests do not require a hosted API.
- **SBOM**: A CycloneDX SBOM is published with the repository when generated by the release workflow.
- **Dependency scanning**: Automated workflows may scan dependencies and container images; no scan frequency or remediation SLA is promised.
- **Supply chain**: The build verifies pinned VeraPDF and Saxon-HE artifacts when configured.
- **Non-root container**: The official Dockerfile runs the application as an unprivileged user.

These practices are implementation facts, not a certification or guarantee of
security, regulatory conformity, or fitness for a particular deployment.

## Scope

This policy applies to the `facturx-engine/facturx-engine` repository and the official Docker image `facturxengine/facturx-engine`.
